# RFC-006: Sovereign Distributed Ledger, In-Browser Signing & Multi-Mirror Publishing (The People's Ledger Protocol)

## 📝 Status: DRAFT (Open for Discussion)

This RFC defines the decentralized distribution, client-side signing, and multi-mirror publishing architecture for the GreyMisnomer protocol. It establishes GreyMisnomer as a **sovereign, zero-cost, locally-deployable, client-verifiable distributed people's ledger**, eliminating reliance on any single hosting provider (such as GitHub) or expensive, complex smart-contract virtual machines (EVM/Solidity).

## 1. Executive Summary & Philosophical Foundations

### 1.1. The "People's Ledger" Manifesto (Why Not EVM?)
Most blockchain and Web3 projects default to deploying smart contracts on an Ethereum Virtual Machine (EVM) network. While EVM provides decentralized execution, it introduces systemic pathologies that disqualify it from being a universal, sovereign public carbon registry:

1. **Artificial Economic Friction (Gas Fees):** Every balance transfer, retirement, or audit check requires burning volatile gas tokens (ETH/MATIC). This penalizes active participation and creates financial gatekeeping.
2. **Infrastructure & RPC Centralization:** In practice, 99% of "decentralized" EVM dApps query centralized RPC node providers (Infura, Alchemy) and centralized indexers (The Graph). If the RPC endpoint censors or goes down, the client fails.
3. **Smart Contract Attack Surface & Upgrade Hazards:** EVM contracts are notorious for reentrancy bugs, proxy storage collision, compiler vulnerabilities, and opaque upgrade multisigs.
4. **Legal & Regulatory Complications:** Token transactions frequently trigger complex Virtual Digital Asset (VDA) taxation, securities classification, and regulatory compliance issues that deter statutory environmental bodies (e.g., BEE, Grid-India, UNFCCC).
5. **Bloat & High Node Barriers:** Running a full archive EVM node requires enterprise-grade hardware, terabytes of NVMe SSDs, and continuous multi-gigabit bandwidth. A local community or small auditor cannot verify the state independently on consumer hardware.

### 1.2. The Sovereign People's Ledger Paradigm
GreyMisnomer rejects the EVM token model in favor of the **Transparency Log / Git-Inspired Architecture** (pioneered by Git, Certificate Transparency [RFC 6962], and Sigstore Rekor):

## 2. Problem Statement (Why This RFC Is Necessary)

While RFC-004 created the append-only event log and RFC-005 added strict Ed25519 authorization, three critical operational bottlenecks remain:

1. **The Single-Point-of-Distribution Vulnerability (GitHub Lock-in):**
   Currently, `events.jsonl`, `events.jsonl.ots`, and `checkpoints/` reside on a single GitHub repository. If GitHub suffers an outage, bans the organization, or experiences state-level censorship, verifiers cannot fetch the log.
2. **The End-User Signing Gap (CLI Exclusivity):**
   In RFC-005, signing an event requires running the Rust CLI (`cargo run --bin grey-misnomer-cli -- sign-checkpoint ...`). Carbon credit project developers, corporate buyers retiring offsets, and field validators cannot be expected to install Rust or compile binaries. Participation requires a seamless, zero-installation, in-browser key generation and transaction signing interface.
3. **The Unspecified Ingestion & Submission Pipeline:**
   RFC-005 defined the schema of signed lines, but did not define how a participant delivers a signed line to the sequencer, how the sequencer validates submissions prior to ledger inclusion, or how rejected intents are signaled.
4. **Mirror Inconsistency & Equivocation Hazards:**
   If multiple mirrors exist, an adversarial sequencer could present Log Fork A to Mirror 1 and Log Fork B to Mirror 2. Verifiers require an automated cross-mirror audit and failover protocol to instantly detect split-view attacks.

## 3. In-Browser Key Management & Transaction Signing Specification

### 3.1. Browser Cryptographic Enclave
In accordance with RFC-005 §3.1, verification **must** run in strict Rust WebAssembly (`ed25519-dalek` with `verify_strict`). For key generation and transaction signing, the browser interface uses a hybrid architecture:

- **Key Generation:** Secure random seed generation using WebCrypto `crypto.getRandomValues(new Uint8Array(32))` passed directly into the WebAssembly runtime to construct an Ed25519 `SigningKey` and derive the matching 32-byte `VerifyingKey`.
- **Identity Storage Model:**
  - *Session Ephemeral (Default):* Held strictly in WASM linear memory.
  - *Encrypted Local Vault (Optional):* Stored in browser `localStorage` encrypted via AES-GCM-256 with a user-provided passphrase (PBKDF2 with 100,000 iterations and SHA-256).
  - *Air-Gapped Key Export:* Keypairs can be exported as raw 32-byte hex or encrypted JSON envelopes containing the public key and encrypted seed.

```json
{
  "version": 1,
  "chain_id": "6713110c8ac6ba73638381f2ec9bde8eb236e894b1a34b4293a9f69933069e95",
  "pubkey": "27ef3b8a333ca785002f12cc9071922848fa2fa460d3eb127994a90f24ee5715",
  "cipher": "aes-256-gcm",
  "kdf": "pbkdf2",
  "salt": "a1b2c3d4e5f60718...",
  "iterations": 100000,
  "ciphertext": "f0e1d2c3...",
  "tag": "8899aabb..."
}
```

### 3.2. Browser Transaction Intent Builder
The web interface (`docs/app.html` & `docs/js/app.js`) provides an interactive Intent Builder that compiles structured human inputs into exact canonical binary preimages (per RFC-005 §3.2) and produces byte-identical JSONL lines ready for submission.

#### Supported Client-Side Actions:
1. **Mint Intent (Accredited VVB):**
   - Inputs: `project_id`, `credit_id`, `data_root` (Merkle leaf), `range_start`, `range_end`, `initial_owner_pubkey`, `poi_hash`.
   - Preimage Tag: `0x12` (`TAG_MINT`).
   - Signer: VVB Ed25519 Secret Key.
2. **Transfer Intent (Credit Owner):**
   - Inputs: `credit_id`, `recipient_pubkey`, `op_index`.
   - Preimage Tag: `0x13` (`TAG_TRANSFER`).
   - Signer: Current Owner Ed25519 Secret Key.
   - Replay Prevention: Monotonic `op_index` auto-populated by querying the current in-memory WASM state of that batch.
3. **Retire / Burn Intent (Credit Owner):**
   - Inputs: `credit_id`, `range_start`, `range_end`, `claim_type`, `beneficiary`, `op_index`.
   - Preimage Tag: `0x13` (`TAG_BURN`).
   - Signer: Current Owner Ed25519 Secret Key.
   - Outcome: Produces cryptographically verifiable Proof-of-Origin (PoO) certificate upon ledger inclusion.

### 3.3. Client Verification Before Submission
Before any signed line leaves the user's browser, the local WebAssembly runtime executes an instant dry-run:
```rust
// In-browser WASM simulation:
apply(&current_state, &parsed_signed_event)
```
If the simulation fails (e.g. wrong `op_index`, insufficient balance, serial overlap, invalid signature, or unregistered VVB), the UI blocks submission, displays the exact `RegistryError` explanation, and prevents rejected submissions.

## 4. Decentralized Ingestion & Submission Protocols

Actors submit their signed event lines using any of three zero-cost channels:

```
               TRANSACTION SUBMISSION CHANNELS

  Actor Browser / CLI
  ┌─────────────────────────┐
  │ Signed JSON Line        │
  │ {"type":"transfer",...} │
  └────────────┬────────────┘
               │
   ┌───────────┼──────────────────────────┐
   │ Channel A │ Channel B                │ Channel C
   ▼           ▼                          ▼
┌──────────────┐ ┌──────────────────────┐ ┌───────────────────────────┐
│ GitHub Issue │ │ Git Pull Request     │ │ Signed Bundle Drop / P2P  │
│ (Zero-install│ │ (Code-reviewed       │ │ (Air-gapped & Offline     │
│  web submission)  auditable trace)    │ │  USB/Sneakernet ingestion)│
└──────┬───────┘ └──────────┬───────────┘ └─────────────┬─────────────┘
       │                    │                           │
       └────────────────────┼───────────────────────────┘
                            ▼
              ┌───────────────────────────┐
              │ Sequencer Ingestion Engine│
              │ 1. In-memory queue audit  │
              │ 2. Canonical line verify  │
              │ 3. apply() state transition│
              │ 4. Append to events.jsonl │
              │ 5. Sign new checkpoint    │
              └───────────────────────────┘
```

### 4.1. Channel A: GitHub Issue Submission (Zero-Install Web UI)
1. The user clicks **"Submit via Web Form"** in `docs/app.html`.
2. The browser packages the signed JSON line and opens a pre-filled GitHub Issue URL with markdown headers:
   ```markdown
   ### GreyMisnomer Signed Event Submission
   ```json
   {"seq":6,"type":"transfer","credit_id":"CR-2026-001","from":"...","to":"...","op_index":1,"owner_sig":"..."}
   ```
   ```
3. A GitHub Actions workflow (`.github/workflows/ingest_event.yml`) triggers on `issues: [opened]`:
   - Extracts the JSON line block.
   - Replays it against `grey-misnomer-cli replay --verify-line "<line>"`.
   - If valid: Appends to `events.jsonl`, updates hash chain, commits, signs checkpoint, and auto-closes issue with status comment.
   - If invalid: Comments the exact cryptographic failure reason and labels the issue `rejected`.

### 4.2. Channel B: Git Pull Request Submission (Institutional & VVB)
1. Institutional actors (VVBs, grid regulators) maintain a local clone or fork.
2. They append the signed line to `events.jsonl` and submit a Pull Request.
3. CI runs the strict quality gates:
   - `cargo test --all`
   - `grey-misnomer-cli replay`
   - Canonical line byte-identity check.
4. If green, the PR is merged into `main`.

### 4.3. Channel C: Air-Gapped Sneakernet Bundle Drop
For offline facilities, government air-gapped enclaves, or rural carbon projects with poor connectivity:
- Signed lines are written to a `.gmline` text file on an external USB key.
- The sequencer imports the file via CLI:
  ```bash
  grey-misnomer-cli append --chain-id <id> --file signed_batch.gmline
  ```

## 5. Decentralized Multi-Mirror Publishing Architecture

To ensure the registry survives without reliance on GitHub, every ledger update is published simultaneously across multiple independent storage tiers.

### 5.1. Storage Tier Topology

| Mirror Tier | Protocol | Primary Host / Gateway | Latency | Persistence Guarantee | Cost |
|---|---|---|---|---|---|
| **Tier 1 (Origin CDN)** | HTTP / Git | GitHub Pages (`docs/`) & Git Repo | < 50ms | High (Active CDN) | $0 |
| **Tier 2 (IPFS Content-Addressed)** | IPFS / libp2p | Pinata, Cloudflare IPFS, `dweb.link` | 200–800ms | Permanent via decentralized CIDs | $0 (Free public pinning) |
| **Tier 3 (Wayback Machine)** | HTTP / Archive | `web.archive.org/web/*` | 1–3s | Legal & historical permanent archival | $0 (Public benefit) |
| **Tier 4 (Bitcoin Anchoring)** | Bitcoin | OpenTimestamps Calendar Pools | ~1 hour | Thermodynamic, immutable proof-of-existence | $0 (Free calendar servers) |

### 5.3. Automated Multi-Mirror CI Workflow
Upon every push to `main` modifying `events.jsonl` or `checkpoints/`:
1. **Step 1: OpenTimestamps Anchor:** Stamped via `ots stamp`.
2. **Step 2: IPFS Pinning ($0):** Uploads `events.jsonl` and `checkpoints/` to IPFS via IPFS CLI or free API pinning services (e.g. Pinata free tier or public IPFS daemon), yielding unique IPFS CIDs.
3. **Step 3: Internet Archive Snapshot ($0):** Invokes the public Wayback Machine Save Page Now API (SPN2):
   ```bash
   curl -s "https://web.archive.org/save/https://greymisnomer.github.io/GreyMisnomer/events.jsonl"
   ```
4. **Step 4: Update Manifest:** Updates `manifest.json` with new CIDs and snapshot URLs, commits, and deploys to GitHub Pages.

## 6. Client-Side Resilient Verification & Automatic Mirror Failover

Every independent client (the in-browser WebAssembly verifier, the CLI replayer, or a third-party monitor) implements resilient multi-source ingestion with automatic failover.

### 6.1. Ingestion Failover Algorithm

```
                 CLIENT DATA INGESTION STATE MACHINE

  ┌─────────────────────────────────────────────────────────────────┐
  │ Try Origin (GitHub Pages): GET /events.jsonl                   │
  └───────────────────────────────┬─────────────────────────────────┘
                                  │
                  ┌───────────────┴───────────────┐
                  ▼ OK                            ▼ Network Error / 404 / 503
    ┌───────────────────────────┐   ┌───────────────────────────────┐
    │ Parse & Verify Log in WASM│   │ Fetch manifest.json from      │
    └───────────────────────────┘   │ secondary source or IPFS      │
                                    └───────────────┬───────────────┘
                                                    │
                                    ┌───────────────┴───────────────┐
                                    ▼                               ▼
                      ┌───────────────────────────┐   ┌───────────────────────────┐
                      │ Try IPFS Gateway 1        │   │ Try Internet Archive      │
                      │ (e.g. dweb.link/ipfs/<CID>)│  │ (web.archive.org snapshot)│
                      └─────────────┬─────────────┘   └─────────────┬─────────────┘
                                    │                               │
                                    └───────────────┬───────────────┘
                                                    ▼
                                    ┌───────────────────────────┐
                                    │ Verify Byte-Identical Line│
                                    │ & Continuous BLAKE3 Chain │
                                    └───────────────────────────┘
```

1. **Attempt 1 (Primary):** Fetch `events.jsonl` from GitHub Pages origin.
2. **Attempt 2 (IPFS Fallback):** If origin is unreachable, timeout occurs, or CORS fails, fetch from IPFS using the configured public gateway pool (`dweb.link`, `ipfs.io`, `cloudflare-ipfs.com`) using the CID recorded in `manifest.json` or local cache.
3. **Attempt 3 (Wayback Machine):** If IPFS gateways are unreachable, fetch the most recent timestamped snapshot from the Internet Archive.
4. **Cryptographic Integrity Anchor:** Regardless of which mirror served the bytes, the client **never trusts the transport**. The client passes the downloaded raw text into `grey_misnomer_wasm::replay_event_log()`:
   - Validates byte-identical canonical lines.
   - Validates BLAKE3 hash chain from Genesis.
   - Validates all Ed25519 signatures.
   - Validates all 7 protocol invariants and Invariants A1–A3.
   - Re-checks against the latest sequencer checkpoint.

### 6.2. In-Browser Equivocation Detection (Split-View Defense)
If an adversarial sequencer attempts a split-view attack by providing different log histories to different mirrors:
1. The browser checks checkpoints from both Mirror A and Mirror B.
2. The browser calls `detect_equivocation_wasm(checkpoints_json)`.
3. If two valid checkpoints share the same `size` but possess different `head_hash`es, or if an older size is not a prefix of a newer size:
   - The UI immediately renders a **Critical Red Equivocation Banner**.
   - Displays the cryptographic Equivocation Proof JSON containing both signed checkpoints.
   - Halts all further state processing. The sequencer's fraud is mathematically proven and permanent.

## 7. Threat Model & Security Analysis

| Threat Scenario | Vector | Mitigation in RFC-006 |
|---|---|---|
| **Host Deplatforming / Deletion** | GitHub terminates the repository or censors the organization. | Complete ledger exists permanently across IPFS and Internet Archive. Any user can clone from IPFS and run the full registry locally. |
| **Sequencer Censorship (Omission)** | Sequencer refuses to include an actor's valid signed event. | The actor possesses the signed intent with timestamp. The actor can publish the signed intent to GitHub Issues, IPFS, or social channels. Censorship becomes publicly observable. |
| **Split-View / Fork Attack** | Sequencer serves Log A to auditors and Log B to users. | Automated cross-mirror checkpoint audit detects equivocation. Dual signed checkpoints at equal heights permanently disqualify the sequencer. |
| **Browser Key Theft (XSS/Malware)** | Malicious script steals private keys in the browser. | Zero `innerHTML` throughout the codebase. Subresource Integrity (SRI) on scripts. Optional encrypted local vault requires password decryption. Ephemeral session mode stores keys only in volatile WASM memory. |
| **Transaction Front-Running / MEV** | Malicious observer copies a transaction and reorders it. | Impossible: Ed25519 signatures bind the exact `credit_id`, `recipient`, `range`, `op_index`, and `chain_id`. A front-runner cannot alter parameters without invalidating the signature. |
| **Denial of Service (Spam Ingestion)** | Attacker floods submission channels with invalid events. | Local in-browser pre-flight check blocks invalid events before submission. CI and sequencer ingest engines drop invalid signatures in $O(1)$ time without modifying state. |

## 8. Comparison: Sovereign People's Ledger vs. EVM Smart Contracts

| Architectural Dimension | GreyMisnomer (RFC-006 Sovereign Model) | Traditional EVM Smart Contract Model |
|---|---|---|
| **Infrastructure Budget** | **$0.00 (Zero hosting costs, zero gas, zero node fees)** | Requires gas tokens (ETH/MATIC) for every transaction; expensive RPC node subscriptions. |
| **Hardware Barrier** | Runs on any consumer device, smartphone browser, or Raspberry Pi. | Requires high-end nodes (32GB RAM, multi-TB NVMe SSDs) for local archival verification. |
| **Verification Speed** | < 15ms in WebAssembly for full state replay. | Seconds to minutes depending on block times, finality rules, and RPC latency. |
| **Attack Surface** | ~1,500 lines of audited pure Rust; strict mathematical invariants. | Complex Solidity smart contracts, EVM opcode quirks, bridge vulnerabilities, proxy upgrade risks. |
| **Data Permanence** | Hash-chained flat files mirrored on Git, IPFS, Archive.org, and Bitcoin. | State stored in ephemeral EVM state tries; prone to state bloat and RPC archival pruning. |
| **Legal / Regulatory Status** | **Pure Software & Accounting Record (Non-Tokenized)**; avoids securities classification and VDA tax. | Token transfers trigger taxable events, token regulations, and securities scrutiny. |
