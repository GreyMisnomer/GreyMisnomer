# RFC-005: Signed Events, Authorization & Checkpoints (Transparency-Log Model)

## 📝 Status: DRAFT (Open for Discussion)

This RFC extends the [RFC-004](rfc-004.md) event log with cryptographic authorization. RFC-004 proves a log was not edited; it does not prove any line was authorized by the party it affects. RFC-005 closes that gap and fixes the log-malleability findings from the 2026-10-19 audit.

- **Status:** Draft  
- **Created:** 2026-10-19  
- **Author:** @PrabhatKarlekar  
- **Related Documents:** [RFC-001](rfc-001.md), [RFC-002](rfc-002.md), [RFC-003](rfc-003.md), [RFC-004](rfc-004.md)  
- **Supersedes (when Accepted):** RFC-004 §3.2 (entry schema), §3.4 (hash preimage), §3.5 (validation rules), §4 (anchoring target)  
- **Target Phase:** Stage 1.5: Public Alpha with Authorization ($0 Infrastructure)  

---

## 1. Problem Statement

RFC-004 gives a tamper-evident, replayable log. Replaying it checks structure (ranges, supply, double-use) but not authority:

1. **No ownership proof.** `owner` is a free string. `transfer` and `burn` carry no sender and no signature. Anyone who can append a line can reassign or retire any active credit, and `apply()` accepts it.
2. **No issuer proof.** `vvb_signature` is an opaque string and `poi_valid` is a boolean the log writer asserts. `apply()` never checks either.
3. **Replayable intent.** Even with signatures, an old valid signature could be re-appended later unless it is bound to a specific state position and registry.
4. **Malleable log lines (audit finding).** Unknown JSON fields, the `retire` alias, and `#`/blank lines pass verification but are not covered by the hash.
5. **Non-canonical hash preimage (audit finding).** The RFC-004 hash covers serde struct field order, not a defined byte format. Reordering a Rust struct field would silently change every hash.
6. **Hollow invariants (audit finding).** Invariants 1 and 7 test dummy inputs rather than the replayed state.
7. **Split view.** A single host (GitHub) or maintainer could show different histories to different readers.

> [!IMPORTANT]
> **Goal:** The party that orders and hosts the log (the sequencer) must be unable to forge, steal, or reassign credits. It may still delay or reorder (see §5, Residual Trust). Anyone can verify this offline with the CLI or in-browser WASM, with no server, DB, or token.

## 2. Proposed Solution

A **transparency-log design** (same family as Certificate Transparency, RFC 6962, and Sigstore Rekor):

```
 Actors sign their own intent        Sequencer only orders + hosts
┌────────────────────────────┐ signed action ┌──────────────────────────┐
│            VVB             │──────────────►│   events.jsonl (append)  │
│           Owner            │               │   checkpoints (signed)   │
│         Authority          │               └────────────┬─────────────┘
└────────────────────────────┘                            │ git clone / mirror / IPFS
                                                          ▼
                                             ┌──────────────────────────┐
                                             │ Any verifier (CLI / WASM)│
                                             │ 1. canonical-line check  │
                                             │ 2. hash chain            │
                                             │ 3. sig + authority check │
                                             │ 4. apply() + invariants  │
                                             │ 5. checkpoint + OTS      │
                                             └──────────────────────────┘
```

- **Identity = Ed25519 public key.** No accounts, no usernames. Ownership means *"can sign for this key"*.
- Every state-changing event carries a signature by the party whose authority it exercises (§3.5).
- **Replay protection** via a per-credit operation index (`op_index`) and a registry-scoped `chain_id` (§3.3).
- **One canonical binary encoding** defines every signed message and every entry hash. JSON is only a transport rendering, and the verifier rejects any line that is not its exact canonical rendering (§3.2, §3.6).
- **Trust roots are explicit and in the log:** a genesis event names the authority key and the sequencer key; the authority registers and revokes VVB keys (§3.4).
- **Signed checkpoints** commit `(size, head_hash)` and are what gets Bitcoin-anchored, replacing the "stamp a growing file" approach (§3.7).

## 3. Detailed Specification

### 3.1. Cryptographic Primitives

| Item | Choice |
|---|---|
| **Signature** | Ed25519, RFC 8032 (pure, no prehash, no context) |
| **Verification mode** | **Strict.** Reject non-canonical $S$ ($\ge L$), non-canonical point encodings, and small-order public keys. Reference: `ed25519_dalek::VerifyingKey::verify_strict` |
| **Public key** | 32 bytes. Text form: 64 lowercase hex chars |
| **Signature** | 64 bytes. Text form: 128 lowercase hex chars |
| **Hash** | BLAKE3-256 (as in RFC-003 / RFC-004). 32 bytes, 64 lowercase hex chars |
| **Randomness** | Key generation only, never in `apply()` or verification |

Verification **MUST** run in the Rust core (native and WASM). Browser WebCrypto Ed25519 is not guaranteed to be strict and **MUST NOT** be the verifier of record.

A public key is valid iff it decodes to a curve point that is not small-order. `transfer` and `vvb_register` **MUST** reject invalid keys (a transfer to an undecodable key would permanently strand the credit).

---

### 3.2. Canonical Encoding (`enc`)

All signed messages and entry hashes are computed over bytes built with these primitives. **No JSON is ever hashed or signed.**

| Primitive | Encoding |
|---|---|
| `u64` | 8 bytes, big-endian |
| `bytes32` / `pubkey` / `hash` | 32 raw bytes |
| `sig` | 64 raw bytes |
| `str` | `u64` byte_length ‖ UTF-8 bytes. No normalization is applied. Must be valid UTF-8 |
| `tag` | `u8` event-type tag (§3.3 table) |

**String limits:** `project_id`, `credit_id`, `chain_name`: 1–64 bytes, charset `[A-Za-z0-9._-]`. Free-text fields (`label`, `beneficiary`, `methodology_hash`, `jurisdiction`): 1–256 bytes. Length-prefixing (as in RFC-003 leaves) removes concatenation ambiguity.

---

### 3.3. Events, Tags and Replay Protection

| Tag | Event | Signed by | Replay Counter |
|---|---|---|---|
| `0` | `genesis` | `authority` (self-signed) | n/a (`seq 0` only) |
| `1` | `vvb_register` | `authority` | `authority_index` |
| `2` | `vvb_revoke` | `authority` | `authority_index` |
| `3` | `mint` | registered VVB | `credit_id` uniqueness + `poi_hash` uniqueness |
| `4` | `transfer` | current owner | per-credit `op_index` |
| `5` | `burn` | current owner | per-credit `op_index` |
| `6` | `authority_rotate` | current `authority` | `authority_index` |
| `7` | `sequencer_rotate` | `authority` | `authority_index` |

Tags are append-only; a tag is never reused or renumbered.

$$\text{chain\_id} = \text{BLAKE3}(\text{enc}(\text{str } \text{"GM/v1/chain"}) \parallel \text{genesis\_body\_bytes})$$

- Every signed message commits to `chain_id`, so a signature made for one registry (e.g., a test registry) is invalid in another.
- `op_index` starts at `0` for each credit batch and increments by `1` on every accepted `transfer` or `burn` of that batch. A signature commits to the exact `op_index` it is valid for. An old signature can never be re-applied, and operations on one credit are totally ordered by their owner.
- `authority_index` starts at `0` and increments on every accepted authority-signed event after genesis.
- **Signatures deliberately do not commit to `prev_hash`.** A signer can sign offline without knowing the log head, and the sequencer cannot invalidate a pending signature by appending unrelated entries.

### 3.4. Trust Roots and Authority Events

#### Genesis (`seq == 0`, `tag 0`)
```
genesis_body = 
    tag(0) ‖ str chain_name ‖ pubkey authority ‖ pubkey sequencer ‖ bytes32 nonce ‖ u64 created_at ‖ sig authority_sig

authority_sig = 
    Ed25519(authority_sk, str "GM/v1/genesis" ‖ str chain_name ‖ authority ‖ sequencer ‖ nonce ‖ created_at)
```

The genesis hash / `chain_id` is the trust anchor. It **MUST** be published out-of-band (README, RFC, release notes) and covered by a Bitcoin anchor. A verifier is configured with the expected `chain_id`; a log whose genesis differs is a different registry, not a corrupted one. `created_at` is informational (no wall-clock use in `apply()`).

#### Authority-Signed Events

| Event | Signed message (after `str "GM/v1/<name>" ‖ chain_id ‖ u64 authority_index`) | Effect |
|---|---|---|
| `vvb_register` | `pubkey vvb ‖ str label` | Adds an active VVB. Rejects duplicates and invalid keys |
| `vvb_revoke` | `pubkey vvb` | Marks VVB revoked, prospectively by log order. Earlier mints stay valid |
| `authority_rotate` | `pubkey new_authority` | Replaces the authority key |
| `sequencer_rotate` | `pubkey new_sequencer` | Replaces the checkpoint-signing key |

`<name>` is `vvb-register`, `vvb-revoke`, `authority-rotate`, or `sequencer-rotate`.

> [!NOTE]
> The authority is the root of trust for who may issue. This matches the centralized CCTS model (RFC-001: Ministry-of-Power-style governance). RFC-005 does not remove trust in the authority or its VVBs. It makes their actions attributable and non-forgeable by the host. A rogue authority registering a rogue VVB is visible in the public log.

### 3.5. Per-Action Authorization

All messages begin with `str "GM/v1/<action>" ‖ bytes32 chain_id`.

#### 1. `mint` (`tag 3`) — VVB Attestation
```
mint_msg = 
    str "GM/v1/mint" ‖ chain_id ‖ str project_id ‖ str credit_id 
    ‖ u64 range.start ‖ u64 range.end ‖ u64 cc_mint_amount 
    ‖ bytes32 merkle_root ‖ u64 leaf_count ‖ u64 mrv_timestamp 
    ‖ str methodology_hash ‖ str jurisdiction ‖ str market_scope 
    ‖ u64 valid_from ‖ u64 valid_until ‖ pubkey initial_owner

mint_body = 
    tag(3) ‖ (mint_msg fields after chain_id) ‖ pubkey vvb ‖ sig vvb_sig
```

- **Rules:** `vvb` MUST be an active registered VVB; `Ed25519.verify_strict(vvb, mint_msg, vvb_sig)`; `range.size() == cc_mint_amount` (tightened from RFC-001's $\le$; see open question Q1); `hash_algorithm` is the constant `"BLAKE3"` and is not on the wire.
- All RFC-001..003 mint rules still apply (global range lock, burned-range check, duplicate `credit_id`, duplicate `merkle_root`).
- **Fields removed from the wire versus RFC-004:** `poi_valid` (replaced by real signature), `status` (derived state, not input), `amount_tco2e` (duplicate of range size), and the PoI-level owner string (replaced by `initial_owner` pubkey). The ZKP freeze (RFC-001 §8) is unchanged: a VVB signature is the Alpha stand-in for PoI validity.
- $\text{poi\_hash} = \text{BLAKE3}(\text{enc}(\text{str } \text{"GM/v1/poi"}) \parallel \text{mint\_msg} \parallel \text{vvb\_sig})$ is stored on the batch (Invariant 7).

#### 2. `transfer` (`tag 4`)
```
transfer_msg = 
    str "GM/v1/transfer" ‖ chain_id ‖ str credit_id ‖ u64 op_index ‖ pubkey new_owner

transfer_body = 
    tag(4) ‖ str credit_id ‖ u64 op_index ‖ pubkey new_owner ‖ sig owner_sig
```

- **Rules:** Batch exists and is active; `op_index == batch.op_index`; `verify_strict(batch.owner, transfer_msg, owner_sig)`; `new_owner` valid and `!= batch.owner`; on success `batch.owner = new_owner`, `batch.op_index += 1`.

#### 3. `burn` (`tag 5`; `retire` alias is removed)
```
burn_msg = 
    str "GM/v1/burn" ‖ chain_id ‖ str credit_id ‖ u64 op_index 
    ‖ u64 range.start ‖ u64 range.end ‖ str beneficiary ‖ str claim_type

burn_body = 
    tag(5) ‖ (fields after chain_id) ‖ sig owner_sig
```

- **Rules:** As RFC-002 slicing/burn rules, plus `op_index` match and `verify_strict(batch.owner, burn_msg, owner_sig)`.
- `beneficiary` and `claim_type` are signed, so the sequencer cannot rewrite who a retirement was claimed for.

### 3.6. Entry Format and Canonical Line

$$\text{entry\_hash} = \text{BLAKE3}(\text{str } \text{"GM/v1/entry"} \parallel \text{u64 } \text{seq} \parallel \text{bytes32 } \text{prev\_hash} \parallel \text{body\_bytes})$$

`body_bytes` is the full tagged body including signatures, so the chain commits to the signatures themselves. Genesis `prev_hash` is 32 zero bytes. This replaces the RFC-004 §3.4 preimage and no longer depends on serde field order.

#### Text Rendering (One line of `events.jsonl`)
```json
{"seq":3,"prev_hash":"<64 hex>","type":"transfer","payload":{"credit_id":"CC-IN-SOLAR-2026-001","op_index":0,"new_owner":"<64 hex>","owner_sig":"<128 hex>"},"hash":"<64 hex>"}
```

#### Canonical-Line Rule
A verifier **MUST**:
1. **Parse the line strictly:** reject unknown keys, duplicate keys, missing keys, wrong types, uppercase or odd-length hex, leading zeros or signs on integers, floats, and non-UTF-8.
2. **Re-render the parsed entry with the canonical renderer** (fixed key order exactly as in the schema table below, no whitespace, integers in decimal, lowercase hex, minimal JSON string escaping per RFC 8785 §3.2.2).
3. **Reject the line** unless the re-rendering is byte-identical to the input line (excluding the single trailing `\n`).

Blank lines, comment lines (`#`), CRLF (`\r\n`), and a missing final `\n` are rejected. Together with the new type values (`retire` no longer exists), this closes the audit's three malleability probes.

#### Payload Keys in Canonical Order

| `type` | `payload` keys, in exact canonical order |
|---|---|
| `genesis` | `chain_name`, `authority`, `sequencer`, `nonce`, `created_at`, `authority_sig` |
| `vvb_register` | `authority_index`, `vvb`, `label`, `authority_sig` |
| `vvb_revoke` | `authority_index`, `vvb`, `authority_sig` |
| `mint` | `project_id`, `credit_id`, `range_start`, `range_end`, `cc_mint_amount`, `merkle_root`, `leaf_count`, `mrv_timestamp`, `methodology_hash`, `jurisdiction`, `market_scope`, `valid_from`, `valid_until`, `initial_owner`, `vvb`, `vvb_sig` |
| `transfer` | `credit_id`, `op_index`, `new_owner`, `owner_sig` |
| `burn` | `credit_id`, `op_index`, `range_start`, `range_end`, `beneficiary`, `claim_type`, `owner_sig` |
| `authority_rotate` | `authority_index`, `new_authority`, `authority_sig` |
| `sequencer_rotate` | `authority_index`, `new_sequencer`, `authority_sig` |

`merkle_root` is 64 hex chars (not a 32-element integer array).

### 3.7. Signed Checkpoints and Anchoring

The sequencer periodically signs a checkpoint:

$$\text{checkpoint\_msg} = \text{str } \text{"GM/v1/checkpoint"} \parallel \text{chain\_id} \parallel \text{u64 } \text{size} \parallel \text{bytes32 } \text{head\_hash} \parallel \text{u64 } \text{timestamp}$$

`size` is the number of entries; `head_hash` is the hash of entry `size - 1`. Published one per file under `checkpoints/<size>.json`:

```json
{"chain_id":"<64 hex>","size":3,"head_hash":"<64 hex>","timestamp":1760832000,"sig":"<128 hex>"}
```

- **Verifier:** After replay, for any checkpoint with `size <= log_size`, the hash at that position **MUST** equal `head_hash` and `sig` **MUST** verify under the sequencer key in force at that position.
- **Equivocation Proof:** Two valid sequencer-signed checkpoints with the same `size` and different `head_hash` are a self-contained, offline-verifiable proof that the sequencer showed two histories. Mirrors and auditors **SHOULD** compare checkpoints.
- **Anchoring (replaces RFC-004 §4):** CI runs `ots stamp` on each new, immutable checkpoint file and commits `checkpoints/<size>.json.ots`. It no longer stamps the growing `events.jsonl`, which left proofs stale after every append. The genesis hash is anchored the same way.
- **Consistency:** The log is a linear hash chain, so consistency between two checkpoints is proven by supplying the entries between them. A Merkle-tree log (RFC 6962 style, succinct proofs) is deferred (§6, Q5).
- **Witnessing (future):** Third parties may co-sign checkpoints (C2SP tlog-witness model). Out of scope for Alpha.

### 3.8. State, Invariants and Verification

#### State Additions to `RegistryState`
- `chain_id`: `[u8; 32]`
- `authority`: `PubKey`
- `sequencer`: `PubKey`
- `authority_index`: `u64`
- `vvbs`: `BTreeMap<PubKey, VvbInfo>` where `VvbInfo { label: String, active: bool }`
- Per-batch fields: `owner: PubKey`, `op_index: u64`, `vvb: PubKey`, `poi_hash: [u8; 32]`

#### Redefined Protocol Invariants (RFC-001 Numbering Unchanged)
Checks now read replayed state, not dummy inputs:

| # | Redefinition |
|---|---|
| **1** | Every batch's `vvb` is in `vvbs` (was registered when minted); every batch has a `poi_hash` |
| **7** | `poi_hash` values are unique across all batches, and spent PoIs are strictly rejected |

#### New Authorization Invariants (Log-Level, Enforced in `apply()` and Re-asserted After Each Event)

| # | Invariant |
|---|---|
| **A1** | Every accepted event carried a signature valid under the key the state required at that position |
| **A2** | For every batch, accepted `transfer`/`burn` events used `op_index` 0, 1, 2, … with no gaps or repeats |
| **A3** | Every signature was bound to this registry's `chain_id` |

#### Verification Algorithm (CLI and WASM, Identical):
1. Check `chain_id` against the configured trust anchor.
2. For each line: canonical-line rule (§3.6) $\to$ `seq` contiguity $\to$ `prev_hash` link $\to$ recompute `entry_hash` from `body_bytes` $\to$ `apply(state, event)` (includes signature and counter checks) $\to$ evaluate all invariants after every event.
3. Verify all checkpoints and any `.ots` proofs available.
4. Report the first failing line/seq (not just the event count).

**New `RegistryError` variants:** `BadSignature`, `UnauthorizedSigner`, `UnknownVvb`, `VvbRevoked`, `BadOpIndex`, `BadAuthorityIndex`, `InvalidPublicKey`, `WrongChain`, `NonCanonicalLine`, `ChainIdMismatch`.

### 3.9. Migration

The RFC-004 sample log is fixture data (placeholder roots and signatures) and cannot be upgraded in place. Stage 1.5 starts a new chain with a RFC-005 genesis. The old file moves to `fixtures/events.v1.jsonl` and is labeled legacy, verified only by a v1 mode in the test suite. v1 and v2 entries **MUST NOT** be mixed in one file.

## 4. Alternatives Considered

- **Option A: Sign the raw JSON line (or JCS canonical JSON) instead of binary preimages.**
  - *Pros:* Simpler; one format.
  - *Cons:* Every language needs a bug-free canonical JSON implementation; Unicode/number edge cases; couples signatures to rendering.
  - *Decision:* **Rejected.** Binary `enc` plus a strict canonical-line check gets both.
- **Option B: Account nonces (global per key) instead of per-credit `op_index`.**
  - *Pros:* Familiar from Ethereum.
  - *Cons:* Forces a global per-key order across unrelated credits; needs an account table.
  - *Decision:* **Rejected.** Credits already have identity.
- **Option C: Sequencer signs every entry.**
  - *Pros:* Simple attribution.
  - *Cons:* Makes the sequencer the authorizer, which is the exact problem this RFC removes.
  - *Decision:* **Rejected.** Sequencer signs checkpoints only.
- **Option D: secp256k1 / Schnorr (Bitcoin-compatible keys).**
  - *Pros:* Reuse Bitcoin tooling.
  - *Cons:* No pressing need; Ed25519 has better library support and safer defaults.
  - *Decision:* **Deferred.**
- **Option E: Multi-sig / threshold authority from day one.**
  - *Pros:* Removes single-key authority risk.
  - *Cons:* Protocol and UX complexity.
  - *Decision:* **Deferred** (§6, Q3).
- **Option F: Put the registry on an EVM chain now.**
  - *Pros:* Real consensus on ordering; smart contracts.
  - *Cons:* Gas, wallets, legal/tax questions (see RFC-004 §1).
  - *Decision:* **Not rejected.** This is the natural Stage 2, where this RFC's message formats become the smart contract's signed-intent specification.

## 5. Threat Model & Residual Trust

| Threat | Mitigation |
|---|---|
| **Sequencer forges a transfer or burn** | No valid `owner_sig`; every verifier rejects (A1) |
| **Sequencer rewrites a beneficiary or claim type** | Signed fields; entry hash covers signatures |
| **Replay of an old signed transfer or burn** | Bound to `op_index` and `chain_id` (A2, A3) |
| **Signature reuse across registries** | `chain_id` in every message |
| **Rogue VVB mints fake credits** | Only authority-registered keys accepted; registration is public and attributable; revocation is prospective |
| **Sequencer inserts, edits, or removes history** | Hash chain, anchored checkpoints, equivocation proof |
| **Split view across mirrors** | Signed checkpoints; two heads at one size prove misbehavior |
| **Unknown fields, `retire` alias, comment lines** | Strict parse plus byte-identical canonical line |
| **Signature malleability, small-order keys** | `verify_strict`; invalid-key rejection |
| **Serde or struct-order change alters hashes** | Hash defined over `enc` bytes, not serde |
| **Hollow invariants** | Redefined over replayed state (§3.8) |

### Residual Trust (Explicit, Not Solved Here):
1. **Censorship and ordering.** The sequencer can delay or refuse to append a valid signed action, or order unrelated actors' events. *Mitigation:* Public submission trail and checkpoint cadence; real fix needs consensus (Stage 2, Option F).
2. **Authority and VVBs.** Trusted for issuance policy. Unauthorized actions by them are visible, not impossible.
3. **Key loss.** Losing an owner key strands that credit. There is no recovery in Alpha (§6, Q2). Key compromise lets the attacker spend until a legitimate transfer lands first.
4. **Time.** `apply()` has no clock. `valid_from`/`valid_until` are signed but not enforced (§6, Q4).

## 6. Open Questions / Points of Discussion

1. **Q1:** Require `range.size() == cc_mint_amount` or keep $\le$ (allowing partial use of an authorization)?
2. **Q2:** Key loss/compromise: authority-signed reassign (centralized recovery) or none?
3. **Q3:** Threshold ($m$-of-$n$) authority and VVB keys: Stage 1.5 or later?
4. **Q4:** How to enforce validity windows with no clock? Options: sequencer-attested time in checkpoints; a `time_attest` event.
5. **Q5:** Move from a linear chain to an RFC 6962 Merkle-tree log for succinct inclusion and consistency proofs?
6. **Q6:** Text address format: hex only (this draft) or bech32 `gm1…` with a checksum?
7. **Q7:** Submission path for signed actions: GitHub PRs, issues, or a signed-bundle drop? Who may run the sequencer role?
8. **Q8:** Does the Oct-2026 direction (decentralized, tokenized) change the Stage 1.5 scope, or is this explicitly the stepping stone to Option F?

## 8. Implementation Notes (After Acceptance)

- **Location:** New `src/core/src/auth.rs` (keys, `enc`, sign/verify), `src/core/src/event_log.rs` (canonical renderer and strict parser), `src/core/src/registry.rs` (state and `apply` checks), `src/core/src/checkpoint.rs`.
- **Dependencies:** `ed25519-dalek` (pinned, `verify_strict`), `getrandom` with the `js` feature in the WASM crate only (key generation). Core stays strictly free of I/O and clocks.
- **Tasks:**
  1. `enc` primitives plus golden vectors (committed JSON file of inputs, preimages, hashes, signatures; generated by reference implementation and cross-checked by an independent implementation, e.g., a Python script, before status moves to Accepted).
  2. Strict parser plus canonical renderer; negative tests for every §3.6 rejection.
  3. Genesis, authority, and VVB events; state additions.
  4. Signed `mint`/`transfer`/`burn` with `op_index`; remove `poi_valid`, `status`, `retire` from the wire.
  5. Redefine Inv1/Inv7, add A1–A3, run invariants after every event.
  6. Checkpoints plus equivocation check; CLI subcommands `keygen`, `sign`, `append`, `verify --chain-id <hex> --checkpoints <dir>`.
  7. WASM: expose verify and sign helpers; frontend role switcher becomes a key switcher (demo keys held in memory, still not a security boundary).
  8. CI: anchor `checkpoints/<size>.json`, not the growing log; run Playwright; update README (BLAKE3, not SHA-256) and repoint RFC-004 links.
- **Tests needed:** Forged transfer, forged burn, wrong-owner signature, replayed signature (same `op_index`), cross-chain replay, revoked-VVB mint, unregistered-VVB mint, small-order key, non-canonical $S$, each malleability probe (unknown field, alias, comment line, CRLF, uppercase hex), checkpoint equivocation, mid-log invariant failure reports the right line.
